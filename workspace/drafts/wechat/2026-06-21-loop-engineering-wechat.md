这两天刷 AI 编程相关内容时，我看到一个说法，挺扎人的：

> 你不应该再给 coding agent 写提示词了，你应该设计能替你提示 agent 的循环。

第一次看会觉得有点夸张。

但如果你最近真的用过 Claude Code、Codex、Cursor Agent，或者让 AI 帮你改过一个稍微复杂点的项目，就会知道它说的不是玄学。

因为现在很多人所谓“用 AI 写代码”，本质上还是自己在当人肉调度器。

你发一句 Prompt。  
AI 改一段代码。  
你运行，报错。  
你把错误贴回去。  
AI 再改。  
你再跑。  

一轮又一轮。

表面上是 AI 在写代码，实际上最累的那个循环还是你。

你负责观察结果、判断问题、补上下文、决定下一步。AI 只是每一轮被你调用一次。

所以这篇文章里最值得记住的一句话，不是“Prompt Engineering 死了”。

不是。

更准确地说，是 Prompt 的位置变了。

以前我们问：怎么写一句更好的提示词？

现在更该问：怎么设计一套机制，让 AI 写错了也能自己检查、自己修、自己停？

这就是最近 AI coding 圈子里越来越多人提到的 Loop Engineering。

我觉得中文可以叫：循环工程。

更土一点，也更准确一点：给 AI Agent 设计工作流水线。

![From Prompting Agents to Loop Engineering](https://pbs.twimg.com/media/HLMKCzNXIAEm_8F?format=jpg&name=large)

## Prompt 没死，只是你不能只会 Prompt 了

很多新概念出来时，大家都喜欢搞一个“旧东西已死”的标题。

Prompt Engineering 已死。  
程序员已死。  
SaaS 已死。  
搜索已死。  

听听就好。

Prompt 当然还重要。问题是，在 Agent 时代，只会写 Prompt 不够了。

过去你可能会琢磨：

“我该怎么描述这个需求，才能让 AI 一次写对？”

但真实工程里，这个问题通常不成立。

复杂一点的代码，AI 很少一次写对。它会漏边界条件，会误解项目约定，会改出新的测试失败，甚至有时候看起来很自信，实际完全没跑通。

所以更靠谱的问题是：

“我能不能让它写完以后自己跑测试，发现失败后继续修，并且在改不动的时候停下来叫我？”

这就是从 Prompt 到 Loop 的变化。

Prompt 是一句指令。

Loop 是一套闭环。

一句指令让 AI 干一次活。闭环让 AI 反复干活，并且知道什么时候该停。

原文里给了一个很简单的定义：

一个 loop，其实就是一个小程序，帮你做四件事。

给 coding agent 发任务。  
读取它产出的结果。  
判断任务有没有完成。  
没完成，就把错误或下一步继续喂给它。  

听着是不是一点也不神秘？

它的核心形状永远差不多：设定目标，执行动作，检查结果，把错误反馈回去，再来一轮。

![Loop 的基本形状](https://pbs.twimg.com/media/HLMIWhvXcAAeuXO?format=png&name=large)

区别只在于，以前这个循环是你坐在电脑前手动做。

现在，你开始把这个循环写出来。

AI 从“聊天对象”，变成了这个系统里的一个执行单元。

这件事挺关键的。

因为它意味着 AI 编程的竞争点开始上移了：不是谁更会哄模型，而是谁更会设计让模型稳定工作的系统。

## 大家说的 Loop，其实不是同一个东西

这里容易吵架。

因为不同人说 Loop，指的可能不是同一层东西。

原文把它拆成了几种演进，我觉得很有帮助。

![Loop 的几种含义](https://pbs.twimg.com/media/HLMI15RWgAAJ5bt?format=jpg&name=large)

早一点的 ReAct，是“思考、行动、观察、再思考”。

AutoGPT 时代，大家第一次大规模感受到“自我提示、自我执行”的诱惑。当然，它也让很多人见识了什么叫“不知道什么时候停”。

后来有些做法会刻意重置上下文，避免 Agent 被自己前几轮的历史拖垮。

再后来，像 Claude Code 里的 `/goal`、`/loop`，开始把节奏和完成条件做进工具里。

再往上，就是 orchestration：一个人发起任务，多个 Agent 分头跑，读 GitHub、看 Slack、跑 CI、开 PR、做总结。

所以 Loop 不是一个单点功能。

它更像一条线：从单 Agent 的自我修正，到多 Agent 的任务编排。

这也是为什么它最近突然重要。

不是因为“循环”这个想法多新，而是 coding agent 终于开始能接住这套流程了。

## 一个能用的 Loop，至少要有 6 个零件

我最喜欢原文这一段，因为它终于把“听起来很酷”的东西拆成了工程部件。

![Loop 的 6 个组成部分](https://pbs.twimg.com/media/HLMJAs9XAAAdDZV?format=png&name=large)

第一个零件，是触发器。

它得知道什么时候开始。

可以是每 30 分钟跑一次，可以是 PR 被打上某个 label，可以是 CI 挂了，也可以是某个文件发生变化。

没有触发器，你只是手动重复执行一次命令。那不叫 Loop，叫你还没自动化。

第二个零件，是隔离环境。

这点特别容易被忽略。

如果你让多个 Agent 同时改同一个代码库，迟早会互相踩文件。真正跑起来以后，每个 Agent 最好有自己的 git worktree，或者独立沙箱。

只要你想并发，隔离就不是加分项，是地基。

第三个零件，是写下来的上下文。

不要指望 Agent 每次都重新理解你的项目。

构建命令是什么？测试怎么跑？哪些目录不能碰？代码风格是什么？发布流程有什么坑？

这些东西要写下来，放在 Agent 每次都能读到的地方。

很多人说“AI 不懂我的项目”，其实不是 AI 不懂，是项目规则根本没被写成机器可读的东西。

第四个零件，是工具连接。

一个真正有用的 Loop，不能只在终端里输出一句“我修好了”。

它得能连 GitHub、CI、issue 系统、数据库、聊天工具。

能自己读失败日志，能自己开 PR，能自己贴结果，能在需要人类介入时把信息推出来。

这一步决定它是 demo，还是工作流。

第五个零件，是独立检查器。

这可能是最重要的一点。

不要让写代码的 Agent 自己判断自己写得好不好。

这就像让学生自己给自己判卷，通常会过于宽容。

更靠谱的方式是：一个 Agent 写，另一个 Agent 查；或者用测试、lint、截图比对、接口探活这种硬检查来判定。

生产里最麻烦的不是“AI 写错了”。

是“AI 写错了，但它以为自己对了”。

第六个零件，是磁盘上的状态。

模型会忘，会话会断，上下文会满。

所以任务跑到哪一步、哪些已经完成、哪些失败过、下一步是什么，都不要只放在聊天记录里。

写进 markdown、看板、队列、数据库，都行。

一句话：状态要落盘。

模型会忘，文件不会。

## 具体一点：PR 保姆怎么做？

讲概念容易飘，原文给了一个很好的例子：PR babysitter。

我觉得翻译成“PR 保姆”还挺形象。

它可以这么跑：

每 15 分钟检查一次带有 `agent-watch` 标签的 PR。

如果 CI 红了，而且原因很明确，就尝试修一次。

如果主分支更新了，就自动 rebase 一次。

它有预算：每个 PR 最多修一次，最多跑 5 分钟，最多改 10 个文件。

它有停止条件：CI 绿了就停；预算用完也停，然后通知人类。

![PR babysitter 示例](https://pbs.twimg.com/media/HLMJEUQXkAAWcKG?format=png&name=large)

这东西不酷炫，但非常实用。

你第二天回来，看到的不是一堆坏掉的构建，而是几个已经修好的 PR，或者几个被清楚标记出来、需要你介入的问题。

这才是 Agent 特别适合做的活。

不是在聊天框里表演“我懂了”，而是安静地处理那些重复、明确、可验证的工程杂活。

类似的还有很多。

CI 健康检查：每 30 分钟拉一次失败构建，把同类错误聚合起来。十个红 PR，如果根因一样，就变成一个问题。

部署验证：每次发布后自动访问关键接口，确认 200、页面内容正常、核心流程没断。

用户反馈聚类：定时拉取群聊、工单、评论，把反馈归类，再映射到对应文档或代码模块。

你会发现，Loop 最适合的不是“发明一个伟大产品”。

它最适合的是：重复出现、边界清晰、结果可检查的任务。

## `/goal` 的本质：把提示词写成合同

原文里还提到了 Claude Code 的 `/goal`。

这东西很值得单独说一下。

比如你在 Claude Code 里写：

```bash
/goal tests in test/auth pass
```

意思不是“帮我看看测试”。

它的意思是：目标是让 `test/auth` 里的测试通过。你去改，去跑，没过就继续，过了再停。

![Claude Code /goal 示例](https://pbs.twimg.com/media/HLMJGlsWgAA9OAD?format=png&name=large)

这时候，一个好的 `/goal` 已经不太像普通 Prompt 了。

它更像一份合同。

合同里至少要写清楚四件事：

你要的最终状态是什么。  
什么证据证明它达到了。  
过程中不能破坏哪些约束。  
最多允许它花多少预算。  

“把这个功能做好”就太虚了。

“让 `npm test` 退出码为 0，只允许修改 `app/api/billing` 和 `lib/billing`，最多改 10 个文件，20 轮后还不行就停下来报告原因”，这才像一个能跑的目标。

这背后其实是软件工程的老问题。

你怎么定义完成？

你怎么验收？

你怎么限制风险？

你怎么让系统失败时可控？

AI 没有消灭这些问题，只是把这些问题放大了。

以前一个人写慢一点，错误也慢一点。现在 Agent 可以跑得很快，所以边界和验收反而更重要。

## 真正贵的不是 token，是循环次数

过去聊 AI 成本，大家喜欢盯着模型单价。

哪个模型便宜？一次调用多少钱？上下文多大？

到了 Loop 这里，成本的算法变了。

真正贵的是它绕了多少圈才做完。

同一个模型，一次通过很便宜。反复试 6 次才收敛，那就是 6 倍成本。

![Loop 成本变化](https://pbs.twimg.com/media/HLMJdWrWEAA_PIO?format=jpg&name=large)

更坑的是弱检查器。

检查太松，坏代码会被放过去。检查太乱，明明已经好了还继续重试。没有失败上限，它就可能一直烧钱。

所以 Loop Engineering 里最值得优化的，不是把 Prompt 写得更华丽。

是把检查条件写得更硬。

好的检查器，是成本控制器。

好的停止条件，是安全带。

这句话我建议直接记下来。

## 什么时候别用 Loop？

别什么都 Loop。

这点也很重要。

如果只是一次性小改动，手动跑一遍 Agent 就够了。为了一个 5 分钟任务搭一整套循环，是给自己加戏。

如果任务本身很探索，比如“分析用户为什么流失”，也不适合直接 Loop。因为它没有明确的完成条件。

没有完成条件，循环就不知道什么时候该停。

还有一种情况：没有便宜的自动检查方式。

如果最后只能靠你肉眼判断，那你其实还在循环里。AI 只是把更多东西堆到你面前。

所以最适合 Loop 的任务，通常有三个特点：

重复发生。  
范围清晰。  
结果可验证。  

CI 修复、部署验证、接口回归、PR 状态检查、依赖升级、批量迁移、文档链接检查，这些都适合。

“帮我做个伟大的产品”，不适合。

至少不适合一开始就丢给 Loop。

![什么时候不该 Loop](https://pbs.twimg.com/media/HLMJgKkWEAAohTF?format=jpg&name=large)

## 程序员的新价值：不是少了，是上移了

很多人看到 Agent 自动写代码，会焦虑：

那程序员是不是不重要了？

我倒觉得相反。

如果你的价值只是写几行样板代码，那确实会越来越危险。

但如果你能设计可靠的 Loop，你会变得更重要。

因为 Loop 跑得越久，错误也会跑得越远。

一个晚上自动写 20 个 PR，听起来很爽。

但如果没有审查机制、没有状态记录、没有停止条件、没有隔离环境，它也可能一个晚上给你挖 20 个坑。

未来的工程师，可能会少写一点具体代码。

但要更多地设计任务边界、验收标准、工具接口和安全阀。

你不是退出生产线。

你是在设计生产线。

这件事没有“十倍程序员”那么刺激，但更真实。

## 如果今天就想试，别从大项目开始

别一上来就搞多 Agent 编排，也别幻想让 AI 一晚上重构整个系统。

从一个很小、很重复、很烦人的任务开始。

比如：

每 30 分钟检查失败的 CI，把同类错误聚合起来。

每次部署后访问几个关键接口，确认返回 200 和页面内容正常。

每天扫一遍 issue，把带特定标签的问题整理成候选任务。

每次 PR 更新后，跑固定测试，失败就尝试修一次。

然后给它加几个硬约束。

最多跑多久。  
最多改几个文件。  
最多尝试几次。  
哪些目录不能碰。  
什么情况下必须停下来叫人。  

再加一个独立检查器。

可以是测试命令，可以是另一个 Agent，也可以是更简单的脚本。

最后，把状态写到文件里。

这就是一个最小可用的 Loop。

不用玄学，也不用神化。

本质上就是工程常识：触发、执行、验证、反馈、停止、记录。

只不过执行者从人，变成了 AI Agent。

## 写在最后

过去一年，很多人还在卷“怎么写出更好的 Prompt”。

这当然还有价值。

但 AI 编程的重点正在往上走。

以后真正拉开差距的，可能不是谁更会和 AI 聊天，而是谁更会设计让 AI 稳定工作的系统。

Prompt 是一句话。

Loop 是一套机制。

一句话可以让 AI 干一次活。

一套机制，才能让 AI 反复干活，还知道什么时候该停。

这就是从 Prompt Engineering 到 Loop Engineering 的变化。

我觉得它会是接下来 AI 编程里非常关键的一条线。

不是因为它听起来新，而是因为它终于把“AI 写代码”从演示，推向了真实工程。

最后留个问题：

你现在工作里，有没有那种“重复、烦人、但结果可检查”的任务？

如果有，它可能就是你第一个 AI Loop 的起点。

觉得这篇有启发，可以转给正在用 Claude Code、Cursor、Codex 的朋友。

别只问 AI：你能不能帮我写代码？

开始问另一个问题：

我能不能设计一个循环，让它自己知道下一步该做什么？
