# Coding Agent 已经不只是「会写代码」了，它正在被装进一套控制系统

> 翻译 + 解读自 DAIR.AI 创始人 Elvis Saravia 的最新长文 *Autonomous Long-Running Coding Agents*。原文写于 2026-06-13，6 万阅读。我加了一些自己写 agent 这半年踩过的坑。

---

最近你大概也注意到了，Claude Code 里多了一个 `/goal`，又多了一个 `/loop`。

Cursor 那边搞 Background Agents，Devin 把任务切成几十个并行 session 在后台跑，Codex 也开始支持长任务。

很多人以为这只是产品功能在卷。但 Elvis 这篇文章说了一句很关键的话——

**自主编程，正在从「更会写 prompt」变成「更会设计控制系统」。**

听起来有点抽象。我把它翻译成人话：

以前我们和 AI 写代码，是你一句、它一句，对话式的。现在的玩法是，你把目标和约束甩给它，它自己跑几个小时甚至几天，最后回来交活。

中间出错了怎么办？它得自己发现、自己修。怎么算"做完了"？得有人提前定义清楚。

这之间多出来的所有东西——目标、评估器、循环、产物、编排——就是 Elvis 说的那个 "harness"，脚手架。

下面我把这篇文章拆成 6 个点讲。

---

## 一、从「写 Prompt」到「写目标」

Claude Code 的 `/goal` 模式，干的事情其实很简单：

人不再一回合一回合地和 agent 对话，而是一次性把这些东西讲清楚——

- 终态是什么样的
- 用什么证据证明做完了
- 哪些约束不能碰
- 给你多少回合、多少预算

Elvis 用了一个特别准的词：**这玩意儿更像合同，而不是更长的 prompt。**

为什么这么强调？

因为弱目标会让模型有空子可钻。它会提前停、抄近路、或者把"成功"重新定义成它能做到的样子。在对话日志里看着挺顺，跑到生产环境就崩。

强目标不一样。它给 agent 一个**可以反复测量自己是否达到**的靶子。

写过基准测试的同学应该懂这个感觉。一个清晰的 metric，比一万句 "please be careful" 管用。

---

## 二、Evaluator（评估器）必须独立出来

长任务 agent 一个最隐蔽的失败模式是：**让模型自己判断自己做没做完。**

千万别这么干。

Elvis 的建议是把评估器拆成独立角色。它可以是另一个 agent、LLM-as-Judge、测试套件、benchmark 脚本，甚至几样混着用。

关键的设计直觉是这样的：

**任务越确定，越用确定性检查；任务越模糊，才用 agent 评估。**

类型检查、单元测试、lint、集成测试——这些能跑就别让 agent 来判。脚本告诉你"测试过了"是金标准，agent 说"看起来没问题"是糖衣陷阱。

但有些活就是没法写脚本。比如：

- 一篇研究报告写得连贯吗？
- UI 实现和设计稿"感觉"一样吗？
- 一个论文复现是不是抓住了核心？

这种就得上 agent evaluator。

最佳实践就是分层：**确定性检查打底，agent 评审兜上层。**

---

## 三、Verifier 决定信任的边界

这一段我读了三遍。

Elvis 说：**Agent 自主性能走多远，取决于你有没有一个可靠的 verifier。**

Agent 可以生成计划、写代码、还能给你解释它为什么觉得做完了。

**但这套解释，不能当成证据。**

证据必须来自外部检查——一个 agent 没法用嘴皮子绕过去的东西。

这话扎心。我自己最早写 agent 工作流的时候，犯过一模一样的错：让模型最后自己出一份"完成报告"，然后我看报告判断是不是 OK。

结果就是模型很会写报告，活儿做得稀烂。

最隐蔽的失败都发生在这个边界上：

- Verifier 太模糊，模型会满足"最容易那种解读"
- Verifier 太狭窄，模型会过拟合到测试，但偏离原意

Elvis 还顺手提了一句让我蛮意外的观察：

> 前沿模型在 verification 任务上仍有明显的 OOD 问题——只要你布置的校验任务在它训练分布之外，模型就会显著掉链子。

所以他押注：**未来一段时间，企业会对"专门 fine-tune 的 verifier"投入巨资。**

我同意。Verifier 这一层，可能就是下一波护城河。

---

## 四、Loop 让自主性持续

Goal 给方向，Loop 让活儿不断。

为什么需要 loop？因为模型经常在事情还没真正完成的时候就停下来——撞回合上限了、信心不够了、上下文吃满了，或者它觉得"差不多就行了"。

Loop 是外面那一层控制系统。它会：醒来 → 看进度 → 跑检查 → 对照目标 → 没达成就把 agent 推回去继续干。

最朴素的版本就是 Ralph 循环：一个 coding agent 加一个确定性条件。

更灵活的版本会塞一个 evaluator agent 进去，由它来推理"现在该往哪儿走"。

Elvis 这里有句话我想原样引一下：

> Long-running autonomy works as repeated effort under supervision from a control layer, not as one continuous act of intelligence.

翻成人话：**长任务自主性，不是一次性的智能爆发，是控制层监督下的反复尝试。**

Agent 还是会失败。但 loop 让系统能注意到失败，然后继续，而不是默默宣告胜利。

---

## 五、Planning 是领域知识进场的地方

这点我特别想替 Elvis 强调一下。

很多人现在觉得 plan 这件事可以全权交给模型。前沿模型给一份计划，看起来挺像样，直接拿来跑。

不行。

Elvis 的判断是：你可以让模型生成计划，但你还是得检查它、挑战它的假设、把成功标准磨得更锋利，然后才交给 loop 去自动执行。

这件事推到极致，会带出一个有意思的结论：

**「模型」不再是单选题，而是一个架构决策。**

- 有的模型擅长 planning
- 有的模型擅长 executing
- 有的模型适合做便宜的 evaluator
- 有的模型在 vision review 上更强

一个好的编排器（orchestrator）应该让你随时换角色，而不是干等某一家厂商出"完美的 coding agent 接口"。

我自己最近写工作流时在认真试 GLM-4.6 做 planner、Sonnet 做 executor 这种组合。早期感受是：你一旦把"模型"拆成多个工种，整个系统的天花板会被显著抬高。

---

## 六、Visual Artifact 是新的控制台

Terminal 日志在并行 agent 时代撑不住了。

你想象一下：5 个 session 同时在跑，每个都有几千行 log。这时候光盯文字流，人类是没法做监督决策的。

Elvis 说，这时候 **artifact 才是真正的控制面**——一个仪表盘，上面有：

- loss 曲线
- benchmark 分数
- 任务状态
- 截图
- 成本估算
- 最近的决策

你不再是事后看报告，而是**实时盯着 artifact 决定什么时候要插手**。

他还给了一个很实用的拆分原则：

**存储和呈现要分开。**

- Markdown / vault 存证据：日志、笔记、计划、结果
- HTML artifact 负责可视化和交互
- Agent 在 Markdown 里搜，人类盯 artifact

UI 任务尤其如此。一张参考截图能比一千字描述更精确地传达设计意图，再配一个 vision-capable evaluator 做对比，能极大减少"组件实现了，但间距、层级、对齐、产品感全错"的常见坑。

---

## 七、Session Mining：让 agent 把过去的失败学会

最后一点我想单独拎出来讲，因为我觉得它特别被低估。

Elvis 把 agent 的历史 session 称作"工作流数据的金矿"。

如果一个 agent 反复在同一个地方失败、忘记同一个检查、走同一条错路——这种规律不应该埋在 log 里。

**做法是把过去 30 天的 transcript 拿来扫一遍，找出反复出现的失败模式，然后回写成项目规则、agent instruction、vault 里的"经验教训"。**

这是一种"不重训模型，但让本地环境越用越聪明"的做法。

我读到这里立刻去看了下自己仓库里的 `CLAUDE.md` 和 `AGENTS.md`，发现有大半的规则其实就是从过去踩坑里手动总结出来的。Elvis 这里只是把它系统化了——**把这件事变成 agent 自己定期做的工作。**

我猜接下来会有一批工具专门做 session mining。

---

## 一份可以照着抄的工作流

Elvis 文末给了一份相当干的 checklist。我直接翻译过来：

1. 别一上来跑全量。先用一个小、便宜的子集试
2. 写目标：可量化的成功标准、明确的约束、回合或时间预算
3. 把 executor 和 evaluator 拆开
4. 在长任务启动**之前**就定义好外部 verifier
5. 能用确定性检查就用，搞不定再加 agent review
6. 强制要求产物：日志、截图、benchmark 曲线、变更文件
7. 挖掘历史 session，把反复出现的教训提升为项目规则

> "这就是『用一个 coding agent』和『工程化一套自主编程系统』的区别。前者给你一段对话，后者给你一套 harness。"

---

## 写在最后

Elvis 这篇也很坦诚地承认：**这些东西并不能解决所有难题。**

Agent 还是会抄近路、提前停、过度自信、对没见过的论文和 benchmark 给出听起来很对其实站不住脚的方案。

「更信任它」解决不了这件事。**「更好的控制系统」可以。**

Goal、Loop、Evaluator、确定性检查、可视化 artifact、session 记忆——这些都不是模型能力，是工程能力。

未来 coding agent 的进化路径，他给了一句很简洁的概括：

> **更强模型 + 更好编排 = 工程师设计出 agent 可以安全运行数小时甚至数天的条件，并且产出可被验证的工作。**

我读完合上电脑的感觉是：做 agent 这事正在从模型工程退回软件工程。

**这反而是好消息。** 软件工程，我们更熟。
