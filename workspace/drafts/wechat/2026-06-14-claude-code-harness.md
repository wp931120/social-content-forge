# Claude Code 被扒了个底朝天，结果只有 1.6% 的代码在「思考」

> 来源：X 上 @omarsar0（DAIR.AI 创始人 Elvis Saravia）的一条线程，下面有人贴出了 UCL 团队的反向工程报告。我看完很受刺激，整理成这篇。

---

最近做 agent 的圈子里在传一件事：UCL 的研究者把泄露出来的 Claude Code 源码，逐行拆开看了一遍。

**结论挺反直觉的——这玩意儿真正用来「让模型做决定」的代码，只有 1.6%。**

剩下 98.4% 全是脚手架。

权限闸门、工具路由、上下文压缩、错误恢复、会话持久化⋯⋯一堆听起来很无聊的工程基础设施。

但如果你最近也在做 agent 框架，或者天天用 Claude Code 写代码，你大概会和我一样，看完这份报告之后改主意：

**模型不是答案，外面那层壳才是。**

---

## 一、最朴素的核心循环

先说一个让我意外的细节：Claude Code 最里面那个 loop，居然是一个 `while True`。

调用模型 → 跑工具 → 把结果塞回去 → 再调用模型。

没有什么花哨的状态机，也没有显式的 plan / replan / refine 三段式。

Devin 那种把重型规划器螺丝拧到执行框架上的做法、LangGraph 那种用图把模型输出强制路由的做法⋯⋯Claude Code 都没干。

它就是把模型放到一个最大决策权的位置，然后**把所有的工程努力，全砸在外面那层壳上**。

---

## 二、那 98.4% 的脚手架在干嘛？

报告里有几个数字让我印象很深：

**权限系统有 7 种模式，还配了一个 ML 分类器。**

为什么这么复杂？因为他们做了用户研究：93% 的弹窗用户都会点「同意」。

那再加一百个弹窗有什么用？答案是没用。

所以他们干脆反着来：**用算法去自动判断哪些操作根本不该弹**，把人的注意力留给真正需要决策的瞬间。

**上下文压缩有 5 层。**

便宜的先上，扛不住了再升级。预算压缩 → 截断 → 微压缩 → 上下文坍缩 → 自动 compact。

我自己写过一些 agent，最痛苦的就是上下文炸了之后那种混乱感。看到这个分层我才意识到：上下文管理本身就该是个**优化系统**，而不是一个一刀切的截断函数。

**子 agent 只把摘要返回主 agent。**

完整的对话日志写到 sidechain 文件里。这就是为什么 Claude Code 的子 agent 看起来「干净」——主线程根本看不到子线程脏活的细节。

代价是什么？token 用量大约是普通会话的 7 倍。

**Resume 不会恢复会话内的权限授权。**

每次重新进入都要重新建立信任。

听起来很反人类，但报告里说：这种摩擦就是设计本身。你不希望一个昨天通过的危险操作，今天毫无提示地继续被允许。

---

## 三、扩展机制按「上下文成本」排序

这点我之前完全没想过。

Claude Code 把扩展机制分成 4 类：

- Hooks：上下文成本 0
- Skills：低
- Plugins：中
- MCP：高

也就是说，**同一个集成需求，能用 hook 解决的就别动 skill，能用 skill 的就别动 MCP**。

为什么？因为模型每多看一行说明，注意力就被稀释一点。

这跟我们做 prompt engineering 的人天天念的那个咒语一模一样：**少即是多，少即是多。**

只是 Claude Code 把它做进了架构里。

---

## 四、所以这件事真正的含义是什么？

报告里那句话我想引一下：

> 当前沿模型在原始编码能力上趋于收敛，差异化来自 harness（脚手架）的质量，而不是模型本身。

我个人觉得这话有点大胆，但也不是没道理。

GPT-5、Claude 4.5、Gemini 3，编码评测分数其实越来越接近。

那为什么用 Claude Code 写代码就是不一样？

不是因为模型聪明 5%，是因为外面那层壳，把模型的「正常发挥」放大了 30%。

---

## 五、给做 agent 的人一些启发

写这篇的时候我在想，普通开发者能从这份报告里学到什么。我自己列了三条：

第一，**别再幻想找到一个「完美的 prompt」了**。如果你的 agent 跑十次有三次失败，问题大概率不在 prompt，在你没给它一个能纠错、能压缩、能优雅失败的环境。

第二，**评估器和执行器最好别用同一个模型训练**。报告里有人提到一句话我觉得很扎心：「评估器和执行器训练分布相同，所以会在一样的地方一起瞎」。靠近确定性的那一层校验（语法检查、运行测试、规则匹配），才是真正失败相关性低的那部分防线。

第三，**记录中间产物（artifact）这件事不能省**。有句话我特别认同：「一个不留草稿的 agent，就像一个把演算纸扔了的同事，你只能欣赏结果，没法 debug 判断。」

---

## 六、最后

我看完这份报告最大的感受是：

**做 agent 这件事，正在从「模型工程」回到「软件工程」。**

模型自己已经够强了，强到我们不需要再绞尽脑汁逼它出活。真正难的，是怎么把它放进一个能容错、能扩展、能演化的工程系统里。

Claude Code 给了一份很好的参考答案。当然不是唯一答案，每个团队都会有自己的风格。

但至少现在我知道一件事：

下一波 agent 红利，**不在模型那边，在脚手架这边**。
